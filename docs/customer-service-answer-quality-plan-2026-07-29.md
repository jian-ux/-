# 智能客服回答质量优化方案

> 文档日期：2026-07-29
> 适用项目：feisheng-bot
> 文档状态：方案草案，尚未实施

## 1. 背景

当前智能客服已经具备安全检查、业务工具、意图匹配、混合检索、RAG 生成、通用兜底和转人工能力，但实际试聊中仍频繁出现以下问题：

- 回答方向正确，但措辞不严谨或承诺过度。
- 检索到了相关资料，但资料不能直接回答客户问题。
- 正常的产品咨询容易进入固定回复或转人工。
- 所有无答案问题共用同一条兜底文案，追问内容与客户问题不匹配。
- 多轮对话依赖关键词和正则，复杂追问容易丢失主体或意图。
- 缺少稳定的评测、反馈、Prompt 版本和知识治理闭环。

本方案的目标不是让模型“永远不犯错”，而是让系统能够稳定地区分：可以回答、需要追问、必须拒答、需要转人工，并保证回答有依据、表达准确、风险可控。

## 3. 根因分析

### 3.1 知识覆盖不足

现有知识能够覆盖电子合同、电子签名、合同签署和部分产品功能，但缺少客户自然会问的销售与落地问题，例如：

- 第一次使用多久能上手。
- 企业认证、培训和实施需要多久。
- 官网、登录入口和试用路径。
- 不同客户类型适合什么方案。
- 手机端、网页端、小程序的能力边界。

当问题没有标准答案时，System Prompt 会要求模型输出 `__NO_ANSWER__`，随后系统替换为固定兜底文案。

### 3.2 知识内容存在风险

部分知识原文包含不准确、绝对化或互相冲突的表述，例如：

- 使用并不存在的《电子合同法》名称。
- “法院是认可的”“签署完成即时生效”等绝对结论。
- “保证真实性、合法性和关联性”等过度承诺。
- 不同条目对存储期限、证明效力等业务口径不一致。

模型会继承并放大这些问题，因此知识治理必须先于 Prompt 调优。

### 3.3 检索相关不等于能够回答

当前候选资料只要综合分数不低于 `0.50` 就可能进入回答上下文，且重排功能关闭。系统可以找到“语义相近”的资料，但无法稳定判断资料是否真正回答了问题。

实际示例：

- “第一次使用多久能上手”检索到“有没有免费试用”，分数为 `0.628`。
- “支持手机端签署吗”第一候选是“手机端退出后能否继续签署”，直接答案排在后面。

现有主题校验只处理少量合同、会员和服务模式冲突，覆盖范围不足。

### 3.4 System Prompt 过于严格且存在冲突

当前 System Prompt 同时要求：

- 证据不足时只输出 `__NO_ANSWER__`。
- 不得编造企业事实。
- 首句必须直接给出结论。
- 禁止使用“可能”等模糊表达。

前两项会提高拒答率，后两项会让法律、合规等问题表达得过于肯定。Prompt 还包含多个硬编码场景补丁，维护成本会随场景增加而持续上升。

### 3.5 兜底回复没有分类

产品能力、上手时间、官网地址、培训安排和操作报错都可能落入同一条固定文案：要求客户补充使用场景、页面提示或截图。

这条文案适合操作故障，不适合销售咨询。问题不在于系统拒绝编造，而在于拒答后没有根据问题类型生成有帮助的下一步。

### 3.6 固定规则范围过宽

以下规则会在检索或模型之前，或者在无知识时，直接返回固定内容：

- 价格、报价、费用和优惠直接转人工。
- 退款、投诉、曝光、律师函和起诉直接转人工。
- 无知识时，`点签、产品、平台、功能、支持、你们的` 等常见词被视为高风险。
- 人工等待和人工处理中只返回状态文案。

固定规则适合安全与确定性流程，但不应代替正常产品问答。

### 3.7 多轮上下文主要依赖规则

当前会话回答最多使用最近 6 条消息，检索历史最多使用 4 条消息，并通过关键词和正则判断“这个、那个、支持吗、多久”等追问。

这种方式可以处理简单省略，但对复杂转折、话题切换、隐含指代和跨轮需求收集支持有限。

### 3.8 缺少质量闭环

项目已经具备基础 RAG 评测和端到端对话评测服务，但还缺少以下运行机制：

- 固定评测集和上线质量门禁。
- 每条回答的点赞、点踩和问题分类。
- 完整 System Prompt、用户 Prompt 和版本记录。
- 初次 RAG 判断、通用兜底和最终回复的完整路径日志。
- 未命中问题的负责人、处理期限和知识发布流程。

现有 AI 日志只把原始客户问题保存到 `prompt` 字段，无法完整复现当时发送给模型的请求。

## 4. 优化目标

### 4.1 业务目标

- 正常产品咨询尽量直接回答，不因普通关键词误转人工。
- 无法给出具体数字时，先说明已知边界，再提出针对性问题。
- 法律与合规回答不作结果保证，但仍能提供有用信息。
- 固定回答只用于安全、合规和明确的流程状态。
- 人工客服收到转接时，能够看到转接原因和已收集信息。

### 4.2 技术目标

- 检索结果不仅相关，而且能够回答客户意图。
- Prompt 可配置、可版本化、可测试、可发布和回滚。
- 回答决策使用结构化结果，不依赖单一字符串信号。
- 上线前通过固定评测集，线上问题能够进入知识治理闭环。

## 5. 目标回答链路

```text
客户问题
  -> 安全与流程状态检查
  -> 意图、产品、客户类型和风险识别
  -> 多轮问题改写
  -> FAQ/文档/操作手册混合召回 Top 10
  -> Rerank 重排序
  -> 答案相关性与证据充分性判断
  -> ANSWER / CLARIFY / HANDOFF / NO_KNOWLEDGE
  -> 场景化 Prompt 生成回答
  -> 事实一致性与安全输出检查
  -> 回复客户并记录完整链路
```

## 6. 分阶段实施方案

### 阶段 0：建立评测基线

从现有会话、31 个未命中问题和核心 FAQ 中整理 150～300 条评测样本，覆盖：

- 产品介绍、功能与适用场景。
- 注册、认证、发起、签署、盖章和归档。
- 试用、培训、实施和上手时间。
- 法律效力、证据和风险边界。
- 价格、投诉、转人工和人工等待。
- 多轮指代、主体切换和换话题。
- 超范围、恶意输入和 Prompt 注入。

每条样本至少标注：

- 是否应该回答。
- 预期来源类型和来源 ID。
- 必须包含与禁止出现的短语。
- 是否需要转人工。
- 预期回答状态。

复用以下现有接口：

```text
POST /api/admin/rag/evaluate
POST /api/admin/rag/evaluate-dialog
```

阶段产物：固定评测集、当前指标报告、失败案例清单。

### 阶段 1：知识库治理与快速修复

1. 审核全部 192 条 FAQ 和 2 份知识文档。
2. 优先修复法律、合同效力、证据、资质和存储期限内容。
3. 为 27 个未解决问题补充标准答案或明确标记为不可回答。
4. 为常见问题增加同义问法、别名和关键词。
5. 按“一个问题、一个事实、一个明确结论”拆分长答案。
6. 增加产品、客户类型、渠道、风险等级、生效日期和审核人等元数据。
7. 区分销售话术、产品事实、操作手册和法律口径，不再混合使用。

法律类标准表达应包含以下边界：

- 可靠电子签名与手写签名或盖章具有同等法律效力。
- 电子合同和相关记录可以作为证据材料提交。
- 是否采信及证明力大小由法院结合具体案情审查。
- 不保证合同必然有效、证据必然采信或诉讼结果。

阶段产物：已审核知识集、知识责任人、知识版本和第一批缺失 FAQ。

### 阶段 2：检索与答案相关性改造

1. 配置并灰度启用 Cross-Encoder Rerank。
2. 对 Top 10 候选重排后再选 Top 3。
3. 增加答案相关性判断，区分“主题相关”和“能够回答”。
4. FAQ、文档、操作手册和图片资料分通道召回并配置权重。
5. 按问答边界重新切分原始文档，避免多个主题进入同一切片。
6. 为知识增加产品、渠道和客户类型过滤。
7. 使用固定评测集校准阈值，不直接凭感觉修改 `0.50` 或 `0.55`。
8. 对重复、冲突、过期和未审核知识降权或禁止召回。

建议新增答案判断结果：

```json
{
  "answerable": false,
  "decision": "CLARIFY",
  "reasonCode": "MISSING_ONBOARDING_DURATION",
  "supportedSourceIds": []
}
```

阶段产物：重排服务、答案相关性判断器、阈值评测报告。

### 阶段 3：System Prompt 与输出协议重构

将当前单一长 System Prompt 拆分为：

- 核心客服身份与表达规则。
- 知识事实与防编造规则。
- 产品与销售咨询规则。
- 操作与故障排查规则。
- 法律与合规规则。
- 情绪和转人工规则。
- 输出格式规则。

主要调整：

- 删除“禁止使用可能”等会导致绝对承诺的要求。
- 法律问题强制使用条件、边界和法院审查说明。
- 已知部分先回答，缺失部分再追问。
- `NO_KNOWLEDGE` 与 `CLARIFY` 分开，不再都使用 `__NO_ANSWER__`。
- 让模型返回结构化决策，程序负责选择最终展示方式。

推荐输出协议：

```json
{
  "decision": "ANSWER",
  "answer": "...",
  "reasonCode": "GROUNDED_ANSWER",
  "sourceIds": [33, 175],
  "needsTransfer": false
}
```

阶段产物：模块化 Prompt、结构化响应协议、法律与销售场景测试。

### 阶段 4：分类兜底与规则收敛

将统一兜底改为按问题类型处理：

| 问题类型 | 处理策略 |
|---|---|
| 操作报错 | 询问页面、操作步骤、报错文字和截图 |
| 产品能力 | 先回答已确认能力，再询问具体使用场景 |
| 试用与上手 | 询问基础签署还是企业部署，提供对应指引 |
| 法律问题 | 回答原则和证据边界，不保证结果 |
| 价格问题 | 公开价格直接回答，定制报价转人工 |
| 信息确实缺失 | 说明需要核实并提供人工入口 |
| 超出业务范围 | 返回对应业务渠道 |

规则调整：

- 从高风险关键词中移除或收窄 `点签、产品、平台、功能、支持、你们的` 等宽泛词。
- 价格问题不再一律转人工，区分公开套餐与定制报价。
- 公司介绍使用意图识别，不再依赖少量固定正则。
- 安全、投诉、法律纠纷和人工状态继续保留确定性规则。
- 将后台 `bot_reply_strategy` 真正接入核心对话链路。

阶段产物：分类兜底服务、精简规则集、可执行回复策略。

### 阶段 5：多轮上下文增强

为会话维护结构化状态：

```json
{
  "activeProduct": "点签电子合同",
  "intent": "TRIAL_CONSULTING",
  "customerType": "ENTERPRISE",
  "confirmedNeeds": ["手机签署"],
  "missingFields": ["使用人数", "功能范围"],
  "lastUnresolvedQuestion": "第一次使用多久能上手"
}
```

主要措施：

- 简单追问继续使用规则，复杂追问使用小模型改写为独立问题。
- 明确识别继续话题、切换主体和新话题。
- 历史摘要与原始消息分开保存。
- 人工转接时同步结构化需求和未解决问题。

阶段产物：会话状态模型、问题改写服务、多轮评测样本。

### 阶段 6：Prompt 管理与质量闭环

新增后台能力：

- System Prompt 查看和编辑。
- Prompt 草稿、版本、审核、发布和回滚。
- 不同场景绑定不同 Prompt 模块。
- Prompt 变更前后评测结果对比。
- 每条回答点赞、点踩和问题标签。
- 未命中问题负责人、处理期限和发布状态。
- 每日固定回复率、拒答率、转人工率和低评分问题报表。

建议新增数据结构：

```text
bot_prompt_template
bot_prompt_version
bot_message_feedback
bot_quality_evaluation_run
bot_quality_evaluation_case_result
```

日志至少记录：

- Prompt 模板和版本。
- 最终 System Prompt 哈希。
- 完整脱敏后的用户 Prompt。
- 原始检索候选和最终来源。
- 初次模型决策、兜底决策和安全检查结果。
- 模型、Token、延迟和成本。

阶段产物：Prompt 管理页面、质量看板、反馈与未命中闭环。

## 8. 验收指标

首轮目标值建议如下，最终阈值应根据评测基线调整：

| 指标 | 目标 |
|---|---:|
| 检索来源 Hit@1 | 不低于 85% |
| 引用来源命中率 | 不低于 95% |
| 回答/拒答决策准确率 | 不低于 95% |
| 有依据回答精确率 | 不低于 95% |
| 应回答问题召回率 | 不低于 90% |
| 不可回答问题拒答精确率 | 不低于 90% |
| 业务范围内固定兜底率 | 不高于 8% |
| 转人工判断准确率 | 不低于 95% |
| 法律类绝对承诺 | 0 |
| PII 泄漏 | 0 |
| 模型调用错误率 | 不高于 1% |

除自动指标外，每次发布还应人工抽检至少 50 条回答，重点检查事实准确、表达自然、风险边界和下一步是否有帮助。

## 9. 建议实施优先级

### P0：立即处理

- 修复法律类和明显错误知识。
- 处理现有 27 个未解决问题。
- 将统一无答案文案改成分类追问。
- 增加第一版固定评测集。
- 保存 Prompt 版本和完整决策路径。

### P1：核心质量改造

- 启用 Rerank。
- 增加答案相关性判断。
- 重构 System Prompt 和结构化输出。
- 收窄高风险关键词和价格规则。
- 将回复策略接入运行链路。

### P2：持续优化

- 增加结构化会话状态。
- 建设 Prompt 管理后台。
- 增加逐条回答反馈和质量看板。
- 建立灰度发布、对比评测和自动回滚机制。

## 10. 推荐首批任务

第一批实施应保持范围可控，建议依次完成：

1. 建立不少于 100 条的第一版评测集。
2. 修复法律效力、法院采信、出证报告和合同生效相关知识。
3. 为“上手时间、培训、试用、官网、登录、认证”等问题增加审核后的 FAQ。
4. 将无答案回复拆分为操作、产品、销售、法律和真正未知五类。
5. 配置 Rerank，并用同一评测集比较启用前后的指标。
6. 将 `ANSWER/CLARIFY/HANDOFF/NO_KNOWLEDGE` 结构化决策接入对话链路。
7. 收窄宽泛高风险关键词，并回归全部安全规则。

完成上述任务后再评估是否更换模型。若知识和检索没有治理，单独换模型只能改善表达，无法稳定解决错误依据和固定回复问题。

## 11. 不建议的做法

- 不要直接降低检索或拒答阈值，这会增加编造和错误回答。
- 不要删除所有固定回复，安全、投诉和人工状态仍需要确定性处理。
- 不要继续在单一 System Prompt 中无限追加规则。
- 不要把未经审核的销售文档直接作为高可信知识。
- 不要只看单次试聊结果，必须使用固定评测集进行前后对比。
- 不要把所有问题归因于模型，也不要在缺少基线时频繁更换模型。

## 12. 预期变化

完成本方案后，系统应表现为：

- 资料充分时直接、准确地回答。
- 资料部分充分时先回答已知内容，再提出针对性问题。
- 资料不足时说明需要核实，不再机械索要截图。
- 法律和合规问题保留必要限定，不作结果保证。
- 正常产品问题不因宽泛关键词误触发固定回复。
- 多轮对话能够保持产品、客户类型和未解决问题。
- 每次 Prompt、知识和检索改动都能通过评测数据证明效果。
